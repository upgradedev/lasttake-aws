# Assurance

This page is for a reviewer checking LastTake against AWS Well-Architected with the Agentic AI Lens, the EU AI Act and data protection law. It expands [README, Assurance and residual gaps](../README.md#assurance-and-residual-gaps). LastTake itself is for a script supervisor and the 1st AD. [Open LastTake on AWS](https://d3kf6hquzlli8g.cloudfront.net/), choose **Start this fictional shoot day**, run the wrap checkpoint, inspect sources, and answer the saved pickup request. Handoff provides the turnover, receipts with an evidence summary, and delivery status. The hosted demo uses offline interpretation with real Strands tool replay and S3 session resume; no footage/audio analysis or downstream completion is established.

Current reliability scope: policy 1.1.0 refuses stale or unbound decisions, records a take with no camera report row as missing evidence, validates dates before an amendment is written, and tells pending, rejected, unknown and bus-accepted delivery apart. Older findings need a fresh checkpoint, and the workspace states why. Historical evidence stays historical. Human UAT is NOT_RUN, which means no person has completed the 22-case manual UAT testbook in [frontend/UAT.testbook.json](../frontend/UAT.testbook.json). That status is separate from automated acceptance: the [current automated acceptance](https://d3kf6hquzlli8g.cloudfront.net/acceptance.html) page compares the live frontend and backend revisions with the latest public receipt. The required pre-existing component disclosures are in [README, Pre-existing components](../README.md#pre-existing-components).

The page holds three tables: what AWS asks of a workload, what the EU AI Act asks of this class of system, and what the data protection regulation asks of anything holding a person's name.

Every row of the Well-Architected and EU AI Act tables names a residual gap, and none is empty. The data protection table answers six questions and has no residual-gap column; its gaps follow the table. Where a control is not implemented, the row says so and says what would be needed, rather than describing an intention in the present tense.

This page makes no claim that the system meets a regulation, and a CI gate, `tools/prose_gate.py`, fails the build on the words that would make that claim. That judgement belongs to an assessment body, and this document is an account of what was built, not a verdict on it.

## EU AI Act, Regulation (EU) 2024/1689

**This is an account of design decisions against named articles. It is not a legal assessment, and no risk classification here is authoritative.** Our own reading is that this system is not high-risk under Annex III, because it makes no decision about a person and the rights check is a record lookup that explicitly refuses to interpret legal sufficiency. That reading is ours. A deployer in a jurisdiction that reads it differently should take advice.

| Article | What it asks | What is built | Residual gap |
| --- | --- | --- | --- |

## Data protection

**The shipped corpus contains fictional people. User-supplied text is not verified to be fictional; do not enter real personal data.**

Every name, identifier, release record and note in `corpus/` is invented. `THE LAST FERRY` is not a production. There is no real footage, no real release, and no customer-derived data of any kind.

This is checked, not only stated. Each corpus file carries a disclaimer field, and CI regenerates the corpus from its committed generator and fails if the result differs:

```bash
python corpus/build_corpus.py && git diff --exit-code -- corpus/
```

| Question | Answer |
| --- | --- |
| What is collected from a visitor? | A bearer session handle, a run identifier, a role selection, and user-supplied fictional actor, reason and document fields. The browser stores only the session handle and a role preference, in local storage. There is no staff authentication; do not enter real personal data. |
| What is stored? | Findings, decisions and events for that run identifier, in DSQL and S3, including user-supplied text that must be fictional for this demo. Supplied documents are kept in S3 as amendments, and paused runs as Strands session files. |
| Where does it live? | Application storage is configured in `eu-west-1`, and the site is served through CloudFront. The browser receives the records it requests. The hosted demo always runs offline and makes no model API calls. Only the CLI `--bedrock` path calls Bedrock; its default model is a global inference profile, which may process text outside `eu-west-1` (ESTIMATE). |
| How long? | Strands session files expire after 90 days, and replaced object versions after 30 days (`infra/stack.yaml`). Events, artifacts and database rows have no expiry. |
| Is anything shared? | The hosted demo runs on AWS with offline interpretation and sends nothing to a model. The CLI `--bedrock` path sends bounded text inputs to Bedrock; no footage or audio is analysed. Events go to an EventBridge bus that has no rule or target. No email or payment integration is active. |
| Logs? | Lambda logs are kept for 30 days (`infra/stack.yaml`). The application prints only exception tracebacks (`src/lasttake/app/handler.py`); no document text, no prompts and no media are logged by design. CloudFront access logging and API Gateway access logging are not configured. |

**Residual gaps.** Nothing checks that supplied text is fictional. Events, artifacts and database rows have no expiry. There is no access log for the site or the API.

**In a real deployment this would change completely**, and the honest statement is that the design here anticipates it without having been tested against it. Real releases name real people, so a production deployment needs a lawful basis, a retention schedule set by the production rather than by a demo lifecycle rule, subject access and erasure procedures, and a data protection impact assessment. None of those exist here, because none of them can be exercised against invented people.
